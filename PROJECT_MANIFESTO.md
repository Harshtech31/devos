# What is DevOS?

DevOS is an open platform for managing modern software development workspaces.

It is not an IDE.

It is not an AI coding assistant.

It is not a cloud platform.

DevOS exists to become the layer that connects all of them.

Its purpose is to provide a universal, portable, reproducible, and AI-ready workspace that works across tools, providers, operating systems, and teams.

---

# Why DevOS Exists

Software development has become fragmented.

A modern developer must configure:

- AI coding assistants
- IDEs
- Cloud providers
- Databases
- Containers
- Kubernetes
- Git providers
- Secrets
- Documentation
- Research tools
- Templates
- MCP servers
- Environment variables

Every project starts with hours—or days—of manual setup.

Every new laptop requires repeating the same process.

Every new team member goes through the same onboarding.

Every company reinvents the same tooling.

This problem continues to grow as the software ecosystem evolves.

DevOS exists to eliminate that friction.

---

# The Vision

We believe a developer should be able to move from an idea to a fully configured development environment in minutes—not days.

A project should define its workspace.

Not a machine.

Not an IDE.

Not an AI provider.

The workspace should contain everything required to build, test, deploy, research, and collaborate.

Changing computers should not require rebuilding an environment.

Changing IDEs should not require reconfiguration.

Changing AI providers should not require migration.

Changing cloud providers should not require redesign.

Developers should own their environments.

DevOS is not another IDE.

DevOS is not another code editor.

DevOS is not another database manager.

---

# Our Beliefs

## Developers Should Own Their Environment

Development environments should belong to the project—not to a specific computer or application.

Every workspace should be portable.

Every workspace should be reproducible.

---

## AI Should Be Replaceable

No developer should be locked into a single AI provider.

AI providers will evolve.

New models will appear.

Old models will disappear.

DevOS should support all of them.

The workspace remains the same.

---

## Open Standards Win

The software industry advances through open standards.

Examples include:

- Git
- Dockerfile
- Kubernetes
- Terraform
- OpenAPI

DevOS aims to become an open workspace standard—not a proprietary ecosystem.

---

## Simplicity Wins

Complexity is the enemy of productivity.

Every feature must justify its existence.

If a feature does not reduce developer effort, it should not exist.

---

## Developers Come First

Every design decision should answer one question:

> "Does this improve the developer experience?"

If the answer is no, the feature should be reconsidered.

---

# Our Principles

## Workspace First

Everything belongs to a Workspace.

The Workspace is the heart of DevOS.

Projects are built around Workspaces.

Tools consume Workspaces.

Developers collaborate through Workspaces.

---

## Provider Agnostic

DevOS belongs to no vendor.

Supported providers should always be interchangeable.

Examples include:

AI

- OpenAI
- Anthropic
- Google
- Ollama
- OpenRouter

Cloud

- AWS
- Azure
- GCP
- Cloudflare

Editors

- VS Code
- Cursor
- Codex
- Claude Code
- Windsurf
- JetBrains

Databases

- PostgreSQL
- MySQL
- MongoDB
- Redis

No provider should become a requirement.

---

## Open by Default

Specifications should be public.

Schemas should be public.

Plugins should be public.

The ecosystem should belong to the community.

---

## Configuration as Code

Configuration should be:

- Human-readable
- Version controlled
- Portable
- Reviewable

Hidden configuration creates hidden problems.

---

## Security by Default

Security should never be optional.

Secrets should never be exposed.

Least privilege should always be the default.

Developers should understand what DevOS is doing.

---

## Extensibility

The core platform should remain small.

Everything else should be plugins.

This keeps DevOS maintainable and adaptable.

---

## Offline First

Core functionality should not require internet access.

Cloud services should extend DevOS—not define it.

---

# What Success Looks Like

A new developer joins a project.

Instead of spending days configuring tools, they:

1. Clone the repository.
2. Open DevOS.
3. Import the workspace.
4. Start building.

Everything else is already configured.

We imagine a future where every software repository contains a DevOS workspace definition.

Every IDE understands it.

Every AI coding assistant understands it.

Every cloud platform understands it.

Every development tool understands it.

Changing tools becomes effortless.

Changing machines becomes effortless.

Developer onboarding becomes effortless.

The workspace becomes the universal contract between projects and tools.

# What We Will Never Do

We will never intentionally lock developers into a vendor.

We will never hide critical functionality behind proprietary formats.

We will never sacrifice openness for convenience.

We will never prioritize marketing over engineering quality.

We will never compromise developer trust.

Trust, once lost, is difficult to regain.

---

# Long-Term Vision

DevOS begins as a specification.

It grows into a reference implementation.

It becomes a platform.

It becomes an ecosystem.

Eventually, it becomes the standard way software projects describe their development environments.

Just as Git standardized version control and Docker standardized containers, DevOS aims to standardize AI-ready developer workspaces.

Not for shareholders.

Not for vendors.

Not for lock-in.

Not for hype.

We are building it because developers deserve a better way to work.

Every design decision should move us closer to that future.

DevOS is not just software.
